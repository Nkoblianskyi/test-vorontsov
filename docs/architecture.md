# Архитектура

## Слои (Feature-Sliced Design)

```
src/
  app/                              маршруты: только сборка экранов
    (workspace)/                    с сайдбаром: invoices, templates, settings
    (editor)/                       полноэкранные редакторы
  views/                            экраны-страницы
    invoices/  model/rows.ts        строки списка, фильтры, суммы по валютам
               ui/                  view, KPI, таблица
    templates/ settings/
  widgets/app-shell/                сайдбар и навигация
  features/
    invoice-editor/
      model/use-invoice-editor.ts   форма, сохранение, статусы, умные умолчания
      lib/                          line-item, edit-targets (клик по листу → поле)
      ui/                           экран + секции формы + всплывающий редактор на листе
    template-editor/
      model/                        ОДНА модель редактора для обоих UI; загрузка логотипа
      lib/read-logo.ts
      ui/studio/                    собственная реализация (секции General / Content)
      ui/reference/                 реализация 1:1 (CSS-модуль, свои примитивы)
    workspace-data/                 операции над несколькими сущностями
  entities/
    invoice/   model/ lib/ ui/      схема, стор, суммы, статусы, лист Classic / Swiss, превью
    template/  model/ ui/ @x/       схема, пресеты, поля контента, стор, логотип
    company/   model/ @x/           реквизиты продавца и умолчания
  shared/                           UI-примитивы, форматирование, даты, цвет, хранилище
```

Правила:

- Импорты идут только сверху вниз: `app → views → widgets → features → entities → shared`.
- **Сущности друг друга не импортируют, кроме как через `@x`.** Лист счёта рисуется по шаблону и печатает продавца, поэтому `invoice` импортирует только из `entities/template/@x/invoice` и `entities/company/@x/invoice`. Обратных зависимостей нет.
- **Операции над несколькими сторами** живут в `features/workspace-data`:
  - удаление шаблона с переносом его счетов на шаблон по умолчанию;
  - сброс демо-данных.

  Стор никогда не лезет в чужую сущность.

- Слайсы импортируются по сегментам (`model/`, `lib/`, `ui/`), без barrel-файлов: так дерево зависимостей видно по пути, а Next не тянет лишнее в клиентский бандл.

## Модель данных

### Шаблон — `TemplateConfig` (`entities/template/model/schema.ts`)

```ts
{
  name, design: "classic" | "swiss",
  primaryColor, secondaryColor, inkColor, paperTint,
  logo: { show, src, monogram, shape, size },
  typeface, typeScale, headerLayout, ruleWeight, density, accentBand,
  payments: { bankTransfer: { enabled, details }, card: { enabled }, paypal: { enabled, email } },
  content: {
    documentTitle, dateFormat,
    fields: Record<ContentFieldKey, { show, label }>,   // 21 элемент листа
    terms, statement,                                  // тексты по умолчанию для новых счетов
  },
}
```

**Одна zod-схема — все пути:**

- форма (`zodResolver`);
- типы TypeScript;
- проверка данных, прочитанных из хранилища.

Поле, добавленное в схему, не может обойти валидацию ни на одном пути.

Какие поля можно скрыть и под каким названием они показаны в редакторе, описано в `content-fields.ts`. Оба редактора строят вкладку Content из этого списка.

### Счёт — `InvoiceInput` (`entities/invoice/model/schema.ts`)

```ts
{
  number, status: "draft" | "sent" | "paid", templateId, currency,
  issueDate, dueDate, reference,
  customer: { name, email, address, taxId },
  items: { id, name, description, quantity, rate }[],
  discount: { type: "percent" | "amount", value },
  taxes: { id, name, rate }[], amountPaid,
  terms, statement,
}
```

Кросс-полевые правила в `superRefine`:

- дата оплаты не раньше даты выставления;
- скидка в процентах не больше 100 %, фиксированная — не больше subtotal;
- уже оплаченная сумма не больше итога.

Уникальность номера проверяется при сохранении, потому что зависит от других записей.

**Статус для отображения** (`lib/status.ts`) складывается из трёх вещей: что сделал пользователь (`draft` / `sent` / `paid`), сколько осталось заплатить и какое сегодня число. Итог — `draft`, `sent`, `partial`, `overdue` или `paid`.

- «Оплачен» решают деньги, а не флаг. Если в оплаченный счёт добавили строку, он снова открыт.
- Редактор при сохранении переводит такой счёт обратно в `sent` и говорит об этом.

## Хранение

Три zustand-стора с `persist` в `localStorage`: `invoice-studio:templates`, `:invoices`, `:company`.

- `browserStorage` (`shared/lib/storage.ts`) никогда не бросает исключений. Приватный режим или переполненная квота превращаются в «не сохранилось» и тост.
- **Прочитанные данные валидируются** (`merge` в каждом сторе) теми же zod-схемами:
  - невалидные счета и шаблоны отбрасываются;
  - если не осталось ни одного шаблона, возвращаются образцы;
  - блоки реквизитов по отдельности откатываются к умолчаниям.

  Устаревшая или отредактированная вручную запись не может уронить рендер листа.

- **Гидратация.** Данные есть только в браузере, поэтому экраны оборачиваются в `ClientGate`: до гидратации рендерится скелетон, без рассинхронизации SSR.
- **Демо-данные** счетов датируются относительно сегодняшнего дня, поэтому «просрочено» и «через 9 дней» верны при любом запуске.

**Как подключить бэкенд.** Методы сторов (`create`, `update`, `remove`, `markPaid`, `duplicate` …) — единственное место записи. Их можно заменить на вызовы API: REST, tRPC или server actions. Компоненты вызывают те же методы и не меняются.

## Рендеринг листа

```
TemplateConfig ─┐
                ├─► InvoiceDocument ─► ClassicDocument (CSS-модуль, em)
Invoice data  ──┘                    └► SwissDocument   (CSS-переменные, мм)
```

- `InvoiceDocument` — чистый компонент без клиентского кода. Один и тот же компонент рисует превью в генераторе, оба редактора шаблона, миниатюры в галерее и печать.
- **Конфиг превращается в CSS-переменные.** Смена цвета перекрашивает лист через CSS.
- `toDocumentData(invoice, company, { placeholders })` отделяет данные листа от формы. Недописанные поля становятся серыми заглушками.
- **A4 в реальных единицах.** `ScaledSheet` рисует лист шириной 210 мм и масштабирует через `transform`. `data-print` и `@page { size: A4 }` оставляют при печати только лист.
- **`data-edit`.** Каждый элемент листа помечен ключом (`item.2.rate`, `buyer.address`, `logo` …). `PreviewStage` передаёт клик редактору, `lib/edit-targets.ts` решает, что с ним делать:
  - править прямо на листе;
  - перейти к полю формы;
  - предложить экран, которому принадлежит этот элемент.

## Деньги

`computeTotals` (`entities/invoice/lib/totals.ts`):

1. строка = `qty × rate`, округление до центов;
2. скидка — процент от subtotal или фиксированная сумма;
3. налоги считаются от суммы после скидки, каждый округляется;
4. total = net + налоги; balance = total − paid.

- **Округление half-up до центов.** Произведение сначала обрезается до 6 знаков, потому что `10.075 × 100` в двоичной арифметике равно 1007.4999…. Строки на листе всегда складываются в итог на листе.
- Недописанные значения (пустое поле → `NaN`) считаются нулём, превью не ломается.
- Скрытие строки в шаблоне не меняет суммы: шаблон управляет видом, а не деньгами.
- Суммы в разных валютах в KPI не складываются.

## Редактор шаблона

`TemplateEditorProvider` (`features/template-editor/model`) используется обоими UI:

- react-hook-form с zod-резолвером, `mode: "onChange"`;
- **история** — стек снимков с дебаунсом 400 мс, до 60 шагов:
  - правка, которая ещё ждёт дебаунса, записывается перед undo, поэтому шаг назад всегда один;
  - флаг `replaying` не даёт записать сам undo как новое изменение;
- **dirty** — структурное сравнение с сохранённым снимком (`deepEqual`, без сериализации data-URL логотипа);
- `save()` валидирует форму, пишет в стор, при ошибке переключает на нужную вкладку и показывает первую ошибку;
- `beforeunload` при несохранённых изменениях (`useUnsavedChangesGuard`); `Ctrl+S`, `Ctrl+Z` / `Ctrl+Shift+Z` (кроме текстовых полей).

## Качество

| Команда             | Что проверяет                                           |
| ------------------- | ------------------------------------------------------- |
| `npm run typecheck` | TypeScript strict                                       |
| `npm run lint`      | eslint: next/core-web-vitals + typescript + react-hooks |
| `npm run test`      | Vitest, 56 тестов доменной логики                       |
| `npm run build`     | production-сборка Next.js 16                            |

Что покрыто тестами:

- **Суммы**: округление, скидки, налоги от net, `NaN`.
- **Статусы**, в том числе снова открытый оплаченный счёт.
- **Схемы**: кросс-полевые правила, проверка сохранённых записей.
- **Нумерация**: префиксы, спецсимволы, чужие форматы.
- **Пресеты**: не трогают тексты, и все образцы валидны.
- **Форматирование дат и денег**, в том числе `-0` и `NaN`.
- **Даты** через DST и високосный год.
- **Контраст WCAG**.
- **Разбор ошибок форм**.
- **Карта кликов** по листу.

UI проверяется вручную по чек-листу ниже. Компонентные тесты — следующий шаг, если проект пойдёт дальше демо.

### Ручной чек-лист

- [ ] Reference: смена цвета, названия, логотипа отражается в превью; Save закрывает; Cancel с изменениями спрашивает.
- [ ] Studio:
  - пресет меняет вид и не трогает тексты;
  - undo / redo, в том числе сразу после правки;
  - Ctrl+S;
  - клик по листу ведёт к настройке.
- [ ] Генератор:
  - итоги в форме равны итогам на листе;
  - клик по строке на листе правит её на месте;
  - дата открывает календарь.
- [ ] Генератор: занятый номер, дата оплаты раньше даты выставления, пустое имя клиента — ошибки на месте.
- [ ] Печать: на странице только лист A4.
- [ ] Список: фильтры, поиск, «оплачен» из строки, дублирование, удаление с подтверждением.
- [ ] Шаблоны: нельзя удалить шаблон по умолчанию; удаление используемого переносит счета на шаблон по умолчанию.
- [ ] Тёмная тема: интерфейс тёмный, лист остаётся светлым.
- [ ] Телефон: панель Preview внизу, полноэкранное превью, правка касанием.

### Известные ограничения

- Две открытые вкладки не синхронизируются: последняя сохранённая перезаписывает хранилище.
- Правка прямо на листе работает мышью и касанием. С клавиатуры тот же путь проходит форма.
